# miso → WebAssembly browser app (example / proof-point)

A real [miso](https://haskell-miso.org/) front-end app — a virtual-DOM counter
component — that `zinc build --target wasm32-wasi` compiles to a browser
**reactor** module and mounts into the page, with **zero toolchain setup** (zinc
provisions the GHC wasm cross-compiler via the `ghc-wasm-meta` Nix flake).

This is the full-framework counterpart to `examples/wasm-browser` (a minimal
hand-written DOM reactor): here zinc builds miso's whole library for wasm —
including its bundled C source, its `arch(wasm32)` FFI variant, `ghc-experimental`
from the wasm toolchain, and the Template-Haskell splice that embeds miso's JS
runtime into the module.

## Build

```sh
cd examples/wasm-miso
zinc build --target wasm32-wasi
```

This produces, in `.zinc/build/`:

- `misoapp.wasm` — the miso reactor (exports `hs_start`; `hs_init` is auto-exported).
- `ghc_wasm_jsffi.js` — the JS-FFI glue generated by the toolchain's `post-link.mjs`.

miso's JS runtime is **baked into the wasm** (miso uses a `$(evalFile "js/miso.js")`
Template-Haskell splice), so unlike a hand-rolled app there is no separate JS file
to ship.

## Serve + open

```sh
cp .zinc/build/misoapp.wasm .zinc/build/ghc_wasm_jsffi.js web/
cd web && python3 -m http.server 8099   # any static server; file:// won't fetch
```

Open <http://localhost:8099>: a miso counter (− / value / +) rendered by Haskell
compiled to wasm. The buttons update the virtual DOM; "console.log hello" calls
`consoleLog` through miso's effect system.

## How it works

`[build.exe.*] wasm-exports = ["hs_start"]` makes the build a reactor
(`-no-hs-main -optl-mexec-model=reactor`, each symbol linker-exported). `main =
startApp defaultEvents app`; the exported `hs_start` is `main`. The page
instantiates the module with a WASI browser shim, then `wasi.initialize` →
`hs_init(0,0)` → `hs_start()`, which mounts the miso component.
