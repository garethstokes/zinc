# zinc -> WebAssembly browser reactor (example / proof-point)

A Haskell program that `zinc build --target wasm32-wasi` compiles to a browser
**reactor** module and runs in a browser, writing to the DOM via JS-FFI — with
**zero toolchain setup** (zinc provisions `wasm32-wasi-ghc` + `node` + the
`post-link.mjs` glue generator through the `ghc-wasm-meta` Nix flake).

## Build

```sh
cd examples/wasm-browser
zinc build --target wasm32-wasi
```

This produces, in `.zinc/build/`:

- `reactorapp.wasm` — the reactor module (exports `hs_start`; `hs_init` is
  auto-exported so the page can start the RTS).
- `ghc_wasm_jsffi.js` — the JS-FFI glue (binds the `foreign import javascript`
  calls), generated by the toolchain's `post-link.mjs`.

## Serve + open

Copy the two build artifacts next to `web/index.html` and serve the dir over
HTTP (a static server; `file://` won't work for `fetch`):

```sh
cp .zinc/build/reactorapp.wasm .zinc/build/ghc_wasm_jsffi.js web/
cd web && python3 -m http.server 8099   # or any static server
```

Open <http://localhost:8099>. The page shows:

> Rendered by Haskell -> wasm. The answer is 42.

written into the DOM by the Haskell reactor.

## How it works

`[build.exe.*] wasm-exports = ["hs_start"]` makes the wasm build a reactor
(`-no-hs-main -optl-mexec-model=reactor`, each symbol linker-exported) instead
of a WASI command module. The page instantiates the module with a WASI browser
shim, then `wasi.initialize` -> `hs_init(0,0)` -> `hs_start()`. Use
`foreign import javascript unsafe` for synchronous JS calls (a plain
`foreign import javascript` is async and needs the RTS promise machinery).
